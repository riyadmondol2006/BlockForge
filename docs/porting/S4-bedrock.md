# S4 - Chunker Bedrock encoding survey (for the Rust port in BlockForge)

Source root: `.../Chunker/cli/src/main/java/com/hivemc/chunker` (JAR deps only: fastutil, guava, gson, caffeine, picocli, lz4, iq80 leveldb). **There are NO resource files** (no json/nbt/csv under src/main): every table is Java code. Tests live in `cli/src/test/java` (`BedrockBlockIdentifierValidationTests`, `MockConverter` = handy oracle/harness).
Area size (Java lines): bedrock/** 22.9k base + 5.1k versioned = ~28k; mapping/** 1.7k; resolver/** 0.9k; base/resolver 4.5k (shared identifier engine 2.3k, blockentity 0.5k, entity 0.4k).

## 1. Bedrock world format as implemented

### 1.1 Files
- `level.dat` = `i32 LE storageVersion` + `i32 LE payloadLen` + uncompressed little-endian NBT (named root compound). Read: skip 8 bytes (`Tag.readBedrockNBT(File)`); write: `Tag.writeBedrockNBT(file, storageVersion, root)`. Storage version from table: 8 (<=1.18.10), 9 (1.18.30-1.19.30), 10 (1.19.40+).
- Version detection (`BedrockDataVersion.detect`): `lastOpenedWithVersion` (list of 5 ints; first 3 used) else `MinimumCompatibleClientVersion`; else assume oldest (1.12). Floor-lookup in a TreeMap of ~65 registered versions (protocol ver, storage ver, optional state-patch sub version). `stateVersion = major<<24|minor<<16|patch<<8|sub` (written into palette `version` int; only 1.20.0 uses sub=33).
- Bedrock NBT everywhere = little-endian, u16 string lengths, no varints (`Reader.toBedrockReader`).
- Input to Chunker is a *directory* with `level.dat` + `db/`. There is **no .mcworld/zip handling** in Chunker (Java zip use is for Java side) -> our Rust must unzip .mcworld (world files at zip root) into a work dir.
- Other level files used: `levelname.txt` (not touched by Chunker), pack json files ignored.
- level.dat fields consumed (`ChunkerLevelSettings.fromNBT` via `readCustomLevelSetting`): RandomSeed (long; int-truncated if StorageVersion<=8), Generator (0 custom legacy,1 normal,2 flat; flat+`FlatWorldLayers==VOID_WORD_STRING` => VOID), `WorldVersion`->FlatWorldVersion, playerPermissionsLevel (inside `abilities` before 1.19.10), experiments compound (caves_and_cliffs byte, next_major_update, updateAnnouncedLive2023, y_2025_drop_2/3, y_2026_drop_2/3/4...), `worldStartCount` (written as 0xFFFFFFFE; seeds entity unique IDs), SpawnX/Y/Z (SpawnY -1 -> 32767), GameType (3/4/6 spectator -> 6 only on 1.18.30..<1.19.50, else 2), LastPlayed, NetworkVersion, `MinimumCompatibleClientVersion`/`lastOpenedWithVersion` written as 5-int lists. (Note: the real world's `FlatWorldLayers` "TheVoid" preset uses encoding_version 6, which does NOT equal Chunker's VOID string -> would be detected FLAT.)

### 1.2 LevelDB opening
- Java uses **iq80 leveldb fork** (`Iq80DBFactory`), `CompressionType.ZLIB_RAW` (block trailer id **4**, raw deflate, no zlib header, = Mojang `ZlibCompressorRaw`), blockSize 160KB, `BloomFilterPolicy(10)`, createIfMissing, writer `writeBufferSize` 400MB, deletes `db/LOCK` first. Reader reads whatever per-block compression ids exist (the trailer byte selects: 0 none, 1 snappy, 2 zlib, 4 raw-deflate); old Bedrock worlds contain id 1/2 blocks too, so a reader must accept {0,1,2,4}. Comparator = default bytewise (`leveldb.BytewiseComparator`, confirmed in test world's MANIFEST). `lz4` dep is NOT used by the Bedrock path (Java side).
- Writer: `database.compactRange(null,null)` at flushLevel if `shouldLevelDBCompaction`; WriteBatch used for per-column metadata. NBT-copy mode (`remapExistingDB`) iterates all keys of an existing db and re-keys dimensions (9/10/13/14 byte keys).

### 1.3 Key encoding (`util/LevelDBKey`, `LevelDBChunkType`)
Chunk keys (all LE): `i32 chunkX, i32 chunkZ, [i32 dimId if dim != overworld], u8 tag, [i8 subchunkY if tag==0x2F]`. Lengths 9/10 (overworld), 13/14 (other dims). Dim ids: overworld(none), nether 1, end 2, custom >= 1000 (registered in key `DimensionNameIdTable` = NBT `{entries:{"name":int}}`, written only for version > 1.26.10).
Tags (hex/dec): 0x2B(43) Data3D, 0x2C(44) Version (1 byte), 0x2D(45) Data2D, 0x2E(46) Data2DLegacy, 0x2F(47) SubChunkPrefix, 0x30(48) LegacyTerrain, 0x31(49) BlockEntity, 0x32(50) Entity (pre-1.18.30), 0x33(51) PendingTicks, 0x34(52) LegacyBlockExtraData, 0x35(53) BiomeState, 0x36(54) FinalizedState, 0x37(55) ConversionData, 0x38(56) BorderBlocks, 0x39(57) HardcodedSpawners, 0x3A(58) RandomTicks, 0x3B(59) Checksums, 0x3C(60) GenerationSeed, 0x3D(61) GeneratedPreCaCBlending, 0x3E(62) BlendingBiomeHeight, 0x3F(63) MetaDataHash, 0x40(64) BlendingData, 0x41(65) ActorDigestVersion, 0x76(118) LegacyVersion.
Non-chunk keys: `~local_player`, `map_<id>`, `portals`, `BiomeIdsTable` (custom biomes, 1.21.110+), `DimensionNameIdTable`, `PosTrackDB-0x%08x` + `PositionTrackDB-LastId` (lodestones), `digp`+x,z[,dim] (actor digest), `actorprefix`+8 bytes (one entity each), (seen in real worlds but ignored by Chunker: `AutonomousEntities`, `Overworld`(limbo entities), `WorldClocks`, `BiomeData`(snow accumulation), `LevelChunkMetaDataDictionary`).
Column discovery (`isColumnKey`): scan whole DB (`fillCache(false)`), accept 9/10/13/14-byte keys that are not `map_/actorprefix/digp/~local_player` and whose tag is SubChunk (10/14 len) or Data2D/Data3D/Entity/BlockEntity (9/13 len); unknown dimension ids skipped. Regions grouped x>>5,z>>5; processed breadth-first, max 4 regions in flight.
Per column reads (point `get`s): Data3D (else Data2D), entities, block entities, subchunk keys for y = -64..63 (as i8; real range used -4..+19 in practice, Nether 0..7).

### 1.4 Value formats
- **SubChunkPrefix**: `u8 version`; v8: `u8 layerCount`; v9: `u8 layerCount, i8 subchunkY`; (v1.17.0-1.17.20 CaC worlds used v8 with Y offset +4 for overworld NORMAL generator, handled by `applyChunkOffset`). Reader supports ONLY 8 and 9 (not v0-7 legacy, not 0x30 LegacyTerrain). Each layer: `u8 header = bitsPerEntry<<1 | isRuntime(1)`; bits in {1,2,3,4,5,6,8,16}; `valuesPerWord=floor(32/bits)`, `words=ceil(4096/vpw)`, words are u32 LE, values never straddle words (3/5/6 bit leave padding); index i -> `x=(i>>8)&15, z=(i>>4)&15, y=i&15` (x*256+z*16+y), value=(word>>>((i%vpw)*bits))&mask. After words: `i32 paletteSize` then that many **named LE NBT compounds** `{name:"minecraft:x", states:{...}, version:i32}` (disk always non-runtime; runtime=true throws). bits==0 (header 0x00): single entry, no words, NO size int? -> code: `bits==0 => size=1` without reading an int, then 1 NBT. Header `127<<1|x` = "empty/inherit" palette (used for biomes).
  - Layer 0 = blocks, layer 1 = liquid layer (water => waterlogged=true merged into block state `waterlogged`; Chunker adds `waterlogged` as a pseudo-state on EVERY identifier, `BedrockNBTBlockIdentifierResolver`). Writer emits layer 1 only if any waterlogged; liquid palette = [air, `minecraft:water{liquid_depth:0}`]. Empty chunk skipped (`shouldDiscardEmptyChunks`).
  - 1.12-style palette entries `{name, val:short}` (no `states`) handled by `BedrockNBTLegacyBlockIdentifierResolver` (`data` pseudo-state) -> legacy tables, only for <=1.12 / LCE conversions (fallback chain `BedrockLegacyFallback...`: if identifier has `data` state try legacy table first).
- **Data3D (0x2B)**, 1.18+: 256 x i16 LE heightmap (written z-outer, x-inner = index z*16+x) then biome palettes back-to-back (24 for overworld, 8 nether, 16 end; each = standard 16^3 palette block with bits/words but entries are raw `i32 LE biomeId`, runtime flag set when writing). Index 0 = lowest subchunk (y=-4). Reader drops trailing empty (127) palettes; writer pads missing with last palette; for non-CaC input pads 4 palettes at bottom.
- **Data2D (0x2D)**, <1.18: 256 x i16 heightmap + 256 x u8 biome (x-then-z order).
- **Version (0x2C)** 1 byte: 37 (1.17), 40 (1.18.30+), 41 (1.21.40), 42 (1.21.120); also `0x76` = 7 always. **Blending data (0x40)** `[0, BLEND]` with BLEND 0(1.18.30),3(1.19),4(1.20),5(1.20.30),6(1.21.50),7(1.21.60),8(1.21.100),9(1.26.30),10(1.26.40). 0x3D = [0]. Chunker **never writes** FinalizedState(0x36), PendingTicks(0x33), RandomTicks, MetaDataHash(0x3F)/LevelChunkMetaDataDictionary, Checksums, BorderBlocks, BiomeState; reads none of them either (pending ticks dropped).
- **BlockEntity (0x31)**: concatenation of named LE NBT compounds (tag `id`="Chest"/"Sign"/..., x,y,z ints). **Entity**: pre-1.18.30 same concat under 0x32; 1.18.30+ (`v1_18_30`): `digp`+x,z[,dim] = concatenated 8-byte actor keys -> each `actorprefix`+key -> one named NBT (`identifier:"minecraft:..", Pos[3 floats], UniqueID long, definitions`). Writer key = BE long `0x100000000 + (uid ^ 0xFFFFFFFF00000000)`; fresh uid = `(0xFFFFFFFF<<32)|counter`; UniqueID must be set in tag.
- Items inside NBT (chests, players): 1.12-style `{Name, Count:byte, Damage:short, Slot, WasPickedUp, tag:{ench:[{id:int,lvl}], display, Damage...}}` (modern Bedrock still writes this form on disk; enchantment ids numeric -> `BedrockEnchantmentIDResolver`).
- `~local_player`: NBT with Pos(floats, y = feet + 1.62001), Motion, Rotation, Inventory/Armor(reversed)/Offhand, DimensionId, PlayerGameMode. `map_<id>` NBT (colors bytearray, scale, dimension (byte <=1.26.10, int after), xCenter/zCenter, mapLocked...). `portals` NBT `{data:{PortalRecords:[{DimId,TpX,TpY,TpZ,Span,Xa,Za}]}}`.

## 2. Class/package structure and inheritance chain
`BedrockEncoders` = TreeMap<BedrockDataVersion, {readerCtor,writerCtor}>; `getNearestEncoder` = floorEntry. Registered encoder roots: 1.12 (base classes), 1.13,1.14,1.16,1.17,1.17.30,1.18,1.18.30,1.19,1.19.80,1.20,1.20.30,1.20.50,1.20.60,1.21,1.21.40,.50,.60,.80,.90,.100,.110,.120,1.26.20,.30,.40,.50,.60. Each `vX_Y/{reader,writer}` has LevelReader/WorldReader/ColumnReader/ChunkReader (+Writer mirror), **strictly linear inheritance** (vN extends v(N-1)), and 90% are empty boilerplate (create* factories returning own subclasses; ~150-190 lines/pkg, 5.1k total). Real overrides only:
- base (1.12): palette v8, Data2D, per-column entity/blockentity concat, `buildResolvers()` wiring (BedrockReaderWriter): legacy block table, legacy item stack resolver, biome/entity/effect/potion/enchant/painting/trim/banner tables, pre-transform manager (reader vs writer), lodestone hooks.
- v1_13: swaps to modern block resolver + NBT resolver with legacy fallback; `BedrockItemStackResolver` (non-legacy items).
- v1_16: lodestone `PosTrackDB` get/create. v1_17: reader `CavesAndCliffs` from experiments; reader chunk Y offset -4 (overworld NORMAL); writer Y +4, writeMetadata (blending 0x3D=0, Version=37, 0x76=7), CaC experiment flag.
- v1_17_30: **subchunk v9** (reader readPalette + Y inside; writer v9 palette), **Data3D** read/write (padding logic above). v1_18: all heights supported, blending always, CaC builtin.
- v1_18_30: **digp/actorprefix entities** read+write, chunk Version 40, blending data record.
- Remaining packages: only `getBlendingVersion()` / `getChunkVersion()` constants (see 1.4) and `readCustomLevelSetting`/`writeCustomLevelSetting` experiment toggles per "drop" (R20Support next_major_update@1.19; R21 updateAnnouncedLive2023@1.20.50 (+armadillo @1.20.60); y_2025_drop_2 @1.21.80, y_2025_drop_3 @1.21.100, y_2026_drop_2 @1.26.20, drop_3 @1.26.40, drop_4 @1.26.60). 1.21.110: custom biomes via `BiomeIdsTable` (`{list:[{id:short,name}]}`).
=> All version-dependence of the *block/item/entity/biome tables* is NOT in the package chain but in `version.isGreaterThanOrEqual(...)` blocks inside resolvers and `VersionedStateMappingGroup`s. A Rust port needs one reader/writer with a `BedrockVersion` + ~6 version-gated knobs (palette v8/v9, Data2D/3D, entity storage, chunk-Y offset, version/blending bytes, experiments), not 28 packages.

## 3. Pre-transform handlers (`base/reader/pretransform`, `writer/pretransform`)
`PreTransformManager.solve(column, ...)` runs after column read (needs neighbour columns/edges for chunk-border blocks; ~1.5k lines). Reader registers (by Chunker block type/group): stem attach <1.16; **fence / nether fence / glass pane & iron bars / tripwire connections inferred from neighbours when <1.26.50** (Bedrock didn't store them); `BedrockStairShapePreTransformHandler` (<1.26.50); fence gate (in_wall); chorus plant, redstone wire sides (`BedrockRedstonePreTransformHandler`), fire connections (<1.26.60); walls (up + wall height, `BedrockWallPreTransformHandler`); snowy grass/podzol/mycelium (block above is snow); doors (hinge/half/open from neighbour half); note block instrument (834-line table: instrument from block below); kelp / twisting / weeping vines / cave vines head-vs-body (needs plant above/below); double-chest type left/right pairing; painting relocation (entity). Writer: only painting relocation. These are what makes Bedrock->Java visually correct for 1.20/1.21 worlds (needed for milestone, except noteblock/stems).

## 4. Identifier tables and the mapping/ package

### 4.1 What the "mapping" tables are
- Pivot ("intermediate") = `ChunkerBlockIdentifier{ChunkerVanillaBlockType enum (~1290 values, Java-flattened names e.g. OAK_DOOR, IRON_CHAIN, with flags: map colour, state set, allFacesSolid), Map<BlockState<?>,BlockStateValue>}` where `VanillaBlockStates` = 160 Java-property-named states (`facing`, `waterlogged`, `age`...) and ~70 enum value classes (`Age_15`, `Axis`, `SlabType`...). Bedrock side = `Identifier{String id, Map<String,StateValue(bool|int|string)> states}` + pseudo-state `waterlogged`.
- Resolver chain (reader): palette NBT `BedrockBlockCompoundTag{compound,waterlogged}` -> `BedrockNBTBlockIdentifierResolver` -> `Identifier` -> `BedrockBlockIdentifierResolver` (Chunker type+states) ; cached (Caffeine). Writer is the inverse; unknown -> logMissingMapping + AIR; custom (non-minecraft:) namespaced blocks pass through as `ChunkerCustomBlockType` when `customIdentifiersAllowed`.
- Palette `version` int is **ignored on read** (table chosen by level.dat version only) -> old-schema palettes in a newer world would miss.
- `mapping/` package (MappingsFile, DimensionMapping*, IdentifierMapping(s), StateMapping(s), TypeMapping(s), Identifier, StateValue*) = **user-supplied JSON override files** (`--blockMappings/-m`, auto-loaded `block_mappings.chunker.json`, `biome_mappings...`, `dimension_mappings...` from the world folder): keys `types`, `state_lists`, `identifiers`, `items`; each entry `{old_identifier,new_identifier,old_state_values,new_state_values,state_list}`; with `$custom_block` wildcard; `inverse()` for writer. Not data; ~1.7k lines Java, optional for a first milestone (port later as ~500 lines serde_json). `resolver/**` (Resolver<T,U> to/from + chain/inverse/cached; PropertyBasedResolver; KeyedHierarchyBasedResolver with per-class TypeHandlers base->leaf) = pure infrastructure; in Rust replace by traits + an enum/registry of handlers (~250 lines).

### 4.2 How the tables are written in Java (exact encoding)
`BedrockBlockIdentifierResolver.registerMappings(Version)` (3234 lines, 886 `BlockMapping.` calls, ~1290 distinct ChunkerVanillaBlockType, ~1375 distinct bedrock id strings, ~700 `register(`). Body is flat statements (no loops/ifs except version gates `if (version.isGreaterThanOrEqual(a,b,c)) { ...flat... }` at 40 version thresholds 1.13.0 ... 1.26.60). Statement kinds:
```
register(M) | registerDuplicateInput(M) | registerDuplicateOutput(M) | registerOverrideOutput(M)
registerOverrideInput(M) | registerOverrideInputOutput(M) | registerDuplicateOverrideInput/Output(M)
extraStateMappingGroup(WATERLOGGED)   // adds waterlogged<->waterlogged(BOOL_DEFAULT_FALSE) to every mapping
M := BlockMapping.of(id, [n1,v1,[n2,v2]], TYPE, [GROUP], [VanillaBlockStates.S, EnumVal.V | Map])
   | BlockMapping.group([n,v,] ImmutableMultimap.<String,ChunkerVanillaBlockType>builder().put(id,TYPE)....build(), [GROUP], [S,V])
   | BlockMapping.flatten(id, n1[,n2], Multimap<S | Pair<S1,S2>, TYPE> (.put(key,TYPE)) , [GROUP], [S,V])
   | flatten(id,n, S, Multimap<key, Pair<V,TYPE>>) | flatten(id,n, List<S>, Multimap<key,Pair<List<V>,TYPE>>)
   | BlockMapping.merge(TYPE, S, Multimap<id,V>[,GROUP])
```
Semantics of one mapping = row `(bedrockId, pinnedBedrockStates{name->bool|int|string, sorted}, chunkerType, pinnedChunkerStates{S->V}, groupRef)`. `register*` flags map to {in2c, c2in} in {Insert, Override, None}: register(Ins,Ins), DuplicateInput(None,Ins) [many chunker types -> one bedrock id on write], DuplicateOutput(Ins,None) [aliases accepted on read], OverrideOutput(Ins,Override), OverrideInput(Override,Ins), OverrideInputOutput(Ov,Ov), DuplicateOverrideInput(Ov,None), DuplicateOverrideOutput(None,Ov). Insert throws on duplicate key; Override throws if no existing key (use as validation in the port).
Lookup (`ChunkerBlockIdentifierResolver.resolve`): per identifier a TreeMap of groups keyed by the *set of pinned state names*, ordered largest set first; for each set read those input states (missing -> skip group), look up value-list -> OutputMapping; then output states = pinned outputs + `group.applyInput(...)` + extra waterlogged group. Reverse direction identical with chunker states (missing chunker state falls back to BlockState default).
State groups (`BedrockStateGroups`, 1128 lines, 142 constants) = `StateMappingGroup.Builder`: `.state(bedrockName, BlockState, TYPE)`, `.multiState(...)`, `.combineInputStates`, `.combineOutputStates(name, S1, S2, TYPE)`, `.defaultInput(name,val)`, `.defaultOutput(S,V)`; 60 are `VersionedStateMappingGroup.Builder().defaults(g).version(new Version(1,20,30), g2)...` (e.g. 1.20.30 `facing_direction`->`minecraft:cardinal_direction`; 1.20.80 drop unused state). Value converters (`BedrockStateTypes`, 960 lines, 97 constants): `new TypeMapping.Builder<I,O>().mapping(bedrockVal, ChunkerEnumVal)...[.defaults(..)].build()` (717 `.mapping` rows; several rows to same output = lossy legacy values; multi-in/multi-out variants).
Item table (`BedrockItemIdentifierResolver`, 1286 lines): same engine, `ItemMapping.of(id,[dataValue,]ITEM_TYPE,[ChunkerItemProperty.X, val])` (728 rows; potions/tipped arrows generated by loops over `ChunkerPotionType` + `BedrockPotionIDResolver`). Biome (`BedrockBiomeIDResolver`, 91 `mapping.put(ChunkerVanillaBiome.X, id)` w/ version gates), entity type (`...EntityTypeResolver` 136 `put(ChunkerVanillaEntityType.X,"minecraft:y")` + numeric id table 136), enchant/potion/effect/trim/banner/painting resolvers (40-100 lines each, same `put` style). Legacy (1.12 numeric): `legacy/BedrockLegacyBlockIdentifierResolver` 1798 lines (321 registers, `data` int state; flatten with `Pair.of(FacingDirection.X, TYPE)` lists), `BedrockLegacyStateGroups` 398, `BedrockLegacyStateTypes` 960 -> **defer**.

### 4.3 Recipe to machine-convert
**Plan A (recommended, exact): execute the Java, dump reflectively.** JDK 25 is installed; gradle caches have guava/gson/fastutil(min)/annotations (caffeine needed from Maven Central). Compile `cli/src/main/java` with javac (skip cli/messenger, leveldb-dependent classes if needed), then a ~150-line `Dump.java` that for each `BedrockDataVersion` in {1.20.0, 1.21.0, 1.21.50, 1.21.90, 1.21.110, 1.21.120, 1.26.50, 1.26.60,...} (or all) does `new BedrockBlockIdentifierResolver(new MockConverter(null), v, true, false)` and reads the protected maps `inputToChunker` / `chunkerToInput` (`Map<id, InputStateGrouping{groups: TreeMap<SortedSet<String>, Map<List<Object>, OutputMapping{identifier, outputs Map<BlockState,Value>, group}>>}>`) + `StateMappingGroup` fields (`states: List<StateMapping{inputStateNames, outputBlockStates, typeMapping{inputToOutput,outputToInput,defaults}}>, defaultInputs, defaultOutputs`) + `extraStateMappingGroup`. Emit one row per `(version, direction, id, stateNames, values, targetType, targetStates, groupId)`; dedupe groups by structural hash and diff versions into `since/until` intervals (rows identical across consecutive versions collapse). Same harness handles items, biomes, entity types, potions, enchants (`mapping` fields are `Map<>`; use reflection `setAccessible`). No regex needed, loops/version gates/Multimap builders are evaluated by Java itself. Output = JSON -> `build`-time generator -> Rust `static` arrays (string table + u16 indices).
**Plan B (pure-text, no JVM):** Python tokenizer over `registerMappings` text: (1) split on top-level `;` statements, (2) track `if (version.isGreaterThanOrEqual(a,b,c)) {` depth to attach `since=(a,b,c)`, (3) parse the call with a tiny recursive-descent parser: identifiers `A.B.method<...>(args)`, generics skipped with bracket balance, args = string | int | `true/false` | dotted symbol (`ChunkerVanillaBlockType.X`, `VanillaBlockStates.X`, `SlabType.DOUBLE`, `BedrockStateGroups.X`) | `Pair.of(a,b)` | `ImmutableMultimap...builder().put(k,v)...build()` | `Map.of`/`List.of`; (4) expand `group/flatten/merge` exactly as `BlockMapping` does (sort pinned states by name; Pair -> two pinned states). Groups: same parser on `BedrockStateGroups`/`BedrockStateTypes` (chained builder calls `.state(...)/.mapping(...)/.version(new Version(a,b,c), <nested builder>)`). Expect ~95% regex-free; risk = Java overload resolution of `BlockMapping.of` with a trailing `Map`/(S,V) (resolve by argument types: symbol prefixes `VanillaBlockStates.`/enum class names). Item/biome/entity files in Plan B: regex `\.put\(([\w.]+),\s*("[^"]+"|\d+)\)`, `ItemMapping.of(` parser.
Keep type/state names as strings (`"OAK_DOOR"`, `"facing_horizontal"`) in the dump; have the Java-side agent's table map them to Java ids (pivot decision, see 9).

## 5. Rust LevelDB layer: crates checked (crates.io queried 2026-10, sources unpacked in ~/bf-conv/scratch/crates/)
- **`rusty-leveldb` 4.0.2 (MIT, 407k dl, active 2026-10, deps: snap, crc32c, bytes...)** - pure Rust, `Options.compressor_list: Rc<CompressorList>` (256 slots, trait `Compressor{encode,decode}` + `CompressorId::ID`), `Options.compressor: u8` selects write id. **Verified by me**: registering a 20-line `RawDeflate` (id 4, `flate2::{read::DeflateDecoder,write::DeflateEncoder}`) opened the real test world db, iterated **511 entries == my independent python count of live keys** (69 subchunk keys). Default list = {0 none, 1 snappy}; add 2 (zlib) too. Cons: `DB::open` always opens read-write (replays WAL, may create files/MANIFEST, creates LOCK) -> **always operate on a scratch copy of db/** (we unzip .mcworld anyway); `DB` is `!Send` (Rc) and `get(&mut self)`: use one reader thread that fetches raw bytes per column and hands `Vec<u8>` to a rayon pool for decode; `new_iter()` + `LdbIterator::{advance,current,seek}` available; `WriteBatch`, `compact_range`, `flush` available; bloom filter policy built in (Mojang's `BuiltinBloomFilter2` name matches usually; unknown name just disables filter).
- `bedrock-leveldb` 0.3.1 (MIT/Apache, 1.1k dl, Jul 2026, edition 2024/rust 1.87, rayon/tokio/memmap2 deps, 8k lines): purpose-built, reads ids 0/1/2/4 natively, has `read_only` open, `for_each_prefix`, `get_many_owned`, parallel scans. **Caveats seen**: on the test world `collect_keys_owned` returned **569 keys vs 511 live (537 incl. 26 tombstoned)** - appears to include shadowed/deleted records in raw scans; it writes with None/Snappy/**Zlib(id 2)**, no raw-deflate (id 4) writer option. Very young; use only after validating iteration semantics. Good candidate for read-only fast path later.
- `mojang-leveldb` 0.7.0 / `bleveldb(-sys)`: C++ FFI to Mojang's fork via cc+bindgen (needs clang/libclang) - avoid (also user wants no C deps). `rocksdb`: C++, cannot read Mojang table compression id 4 without patches - avoid. `leveldb`/`leveldb-sys` (google C++, no id 4) - avoid. `bedrock-world` 0.3.5 (same org as bedrock-leveldb, 20k lines, async chunk/NBT lib) - unsure value; do not depend on it.
- **Decision**: `rusty-leveldb` (+ `flate2` raw deflate for id 4/2, `snap` already its dep) behind our own thin `BedrockDb` trait (`iter_keys`, `get`, `put`, `delete`, `write_batch`, `compact`) so `bedrock-leveldb` can be swapped in. Write path: set `opt.compressor = 4` (matches Chunker/Mojang) - **unverified that Bedrock itself loads rusty-leveldb output** (log/manifest/table format is standard LevelDB, compressor id in trailer; Mojang registers id 4 and 2 per bedrock-leveldb docs).

## 6. Proposed Rust layout
```
src/convert/bedrock/
  mod.rs                 // BedrockVersion (data-version table: protocol, storage, state patch), detect(), encoders()
  db.rs                  // BedrockDb: rusty-leveldb wrapper, raw-deflate/zlib/snappy compressor list, scratch-copy open, key scan, batch write   (~250)
  keys.rs                // ChunkKey enum/tag consts, key builders/parsers, is_column_key, DimensionRegistry bedrock ids (~250)
```

## 9. Biggest unknowns / risks
1. **Pivot type**: Bedrock tables output `ChunkerVanillaBlockType` (+Java-named `VanillaBlockStates`). BlockForge must adopt this pivot (or compose Bedrock rows with the Java agent's Chunker-Java rows into direct Bedrock<->Java rows at generation time). Need the S-agent for Java area to agree on type/state naming; type names appear to be Java ids upper-cased but with exceptions (e.g. `MOVING_BLOCK_BEDROCK`, `MOVING_PISTON_JAVA`, CUSTOM types) - must verify.
2. Plan A needs Chunker to compile outside gradle (missing caffeine/iq80 jars; fastutil-min may lack classes) - mitigate by downloading jars from Maven Central; fallback Plan B.
3. rusty-leveldb on huge worlds (perf; single-thread `!Send`; memory with bloom/block cache) and write-side interop with Bedrock itself (untested). Chunker writes 400MB write buffer + compaction; ours must not leave huge WAL.
4. Missing keys on write (FinalizedState 0x36, MetaDataHash/LevelChunkMetaDataDictionary): Chunker omits them; real 1.26 worlds contain them (test world: FinalizedState=2 for every column, Version=42, blending [0,9|10]). Unknown whether Bedrock regenerates/decorates unfinalized chunks - plan to write FinalizedState=2 (safe-ish, unverified).
5. State-schema drift: table is selected from `lastOpenedWithVersion`, palette `version` ignored; a world opened by newer game but containing never-resaved old chunks would have mixed schemas (some blocks unmapped -> AIR + log). Consider also trying the next-lower table as fallback.
6. Biome palette `127` = "same as previous subchunk" in real Bedrock; Chunker treats it as empty and prunes only trailing ones - mid-column inherit is lossy (needs care in port: copy previous).
7. Unsupported on read: sub chunk versions 0-7, LegacyTerrain, pending ticks, random ticks, hardcoded spawners; Education blocks; custom blocks beyond passthrough; behaviour-pack scripting/functions.
8. ChunkerVanillaBlockType data includes fictional-looking recent content (cinnabar, sulfur, poplar, icicle, ... 1.26.20-1.26.60); fine, generated from source, but cannot be validated against anything but the validation tests.
